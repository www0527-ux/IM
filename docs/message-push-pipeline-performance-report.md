# 2026-11-09 消息推送优化与验收

这一轮保留 MySQL 提交后返回 stored ACK 的边界，优化普通消息写入、Kafka 发布和消费确认。默认配置两轮突发对照中，100 并发热门会话的观察客户端接收 P95 从 1575～1654ms 降到 270～282ms，20 会话从 1609～1639ms 降到 350～409ms。默认配置 300 条/秒、每场景一分钟的热门会话/多会话测试，共 36000 条全部收到，P95 分别为 102/238ms；600 条/秒的热门会话一分钟候选测试失败，未采纳该调参。低并发多会话未显示稳定改善，不能说所有场景都更快。

## 对照范围

- 基线：本机源码备份 `C:/Users/21201/Downloads/IM/IM/im-push-pipeline-backup-20261109-204320`，已包含普通消息会话批处理和群成员缓存。本轮不是去 Outbox 前后对照。
- 当前：普通消息分片批次共用事务、多会话计数器批量 SQL；Publisher 聚合最多 32 条/1ms；Consumer 有界预取、串行业务处理、32 条/10ms 同步批量确认；Realtime 正式应用 Log 配置。各项共同作用，未分离单项收益。
- 同一 Windows 主机与 Docker Desktop（8 CPU、约 8GB）、Go 1.26.5、MySQL 8.4.7、Kafka 3.9。连接池 Realtime/RPC/Offline 为 24/16/16；Kafka 三分区、一副本；MySQL `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`。
- 每次使用独立数据库、Topic、消费组、etcd 注册 Key 和缓存失效频道。只创建隔离测试资源，没有清空业务库或停止共享基础设施。
- 100 个发送用户、101 个群成员，每条群消息向其余 100 个成员推送。延迟从发送连接实际发送开始，到独立观察连接收到 `message.new` 为止。只对该观察连接逐条核对，不能推导所有设备均收到。
- 每条正文 128 字节。每组先预热 100 条并等待排空；正式数据排除预热。发送仍经过真实 WebSocket 鉴权、发送权限 RPC、MySQL、Kafka 和 Push，另经 Offline HTTP 主动同步核对内容。
- 不统计生产网络延迟、移动设备、跨机房、多实例、故障集群或长期运行。单副本 Kafka 的测试不证明多副本高可用性能。

## 保留失败与中间结果

- `burst-20261109_205622`：只做发布/确认优化，尚未修正 Realtime 日志初始化。发现 YAML 的 `Log.Level: error` 原来没有实际生效。
- `burst-20261109_210120`、`sustained-20261109_210455`：中间版本曾调用整套 `ServiceConf.SetUp()`。后者当前版本在 600/秒出现连接关闭和发送器在途上限，下一组预热失败，不能算全部通过。随后仅初始化日志，避免引入原 Realtime 没有开启的运行时组件；不能将全部差异归因于日志或某个组件。
- `sustained-20261109_211917`：带诊断与 CPU profile 的热门会话 600/秒、10 秒采样，属于定位实验。Windows 网络写调用占用显著，不能由这次短采样推导数据库已无瓶颈。
- `sustained-20261109_212222`：只初始化日志的版本，热门会话 600/秒、20 秒接收 P95 为 116.37ms，20 会话同速率仍为 2576.26ms，并有 575 次请求失败。
- `sustained-20261109_212941`：仅合并多会话事务、仍逐会话执行计数器 SQL，600/秒多会话 P95 为 2702.63ms，有 1743 次连接关闭错误。此后才合并计数器 SQL。

## 复核入口与本阶段决策

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/push-pipeline-compare.ps1 -Mode Burst
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/push-pipeline-compare.ps1 -Mode Sustained -Rates 300,600 -Groups 1,20 -Seconds 20
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/push-pipeline-compare.ps1 -Mode Sustained -CurrentOnly -Rates 300 -Groups 1,20 -Seconds 60 -WriterBatchSize 32
node scripts/summarize-push-pipeline.mjs <本机运行目录>
```

实现与回退参数见 [设计说明](message-push-pipeline-design.md)。决策是保留 MySQL 的消息/Seq 与资金事实边界，优先合并热路径中的数据库和 Kafka 往返。代价是普通消息同批不同会话共享回滚/等待范围，Consumer 批量确认扩大重放窗口；通知仍是尽力传播。是否适合目标部署环境，应由该环境的持续负载和真实接收结果决定。
