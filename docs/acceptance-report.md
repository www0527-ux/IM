## 修复的问题

### 1. 领取与退款的数据库时间扫描

领取与退款原先将 `SELECT NOW(3)` 直接扫描到 `time.Time`。真实运行时 go-zero 将其当作结构体映射，返回 `not matching destination to scan`，领取事务随即回滚。同类写法也存在于退款事务。

两处改为使用带 `db:"db_now"` 字段的结构体接收 `SELECT NOW(3) AS db_now`。修复没有改变红包行锁顺序、事务边界或最终 SQL 的过期条件检查。真实领取、并发退款和领取过程中到期的验证覆盖了修复后的路径。

- `service/redpacket/application/receive_service.go`
- `service/redpacket/application/expire_service.go`

### 2. Kafka 网络 EOF 被误判为 Reader 关闭

完整重跑 `20261005_221019` 中，前 15 项通过，Kafka 停机恢复项超时。Realtime 日志显示 Push Reader 收到 `EOF` 后让整个服务退出，红包资金与 Outbox 仍保留，但 Writer 已无法补齐消息。

检查当前 `kafka-go` 源码发现：内部消息读取路径会将网络 EOF 转为 `io.ErrUnexpectedEOF`，消费组协调的 `runError` 路径却可能原样返回 EOF。因此只根据 `errors.Is(err, io.EOF)` 不能确认 Reader 被主动关闭。

新增 `common/kafkareader`，由封装记录程序主动 `Close` 的状态。未主动关闭时，将 Fetch/Commit 的 EOF 视为网络中断并交给原有重试循环；主动关闭后返回关闭错误。Realtime 三个 Reader 和红包 Worker 共用该封装。消费组代次失效的停止策略保持原样。新增回归测试验证网络 EOF 后仍处理当前消息、提交重试不重复业务、显式关闭则停止。

## Redis 故障的实际边界

缓存 Key 缺失可以回源 MySQL；整个 Redis 服务宕机则还会影响登录状态鉴权和 User RPC 的缓存模型。不能将当前实现描述成“Redis 整体宕机时所有发送、领取和同步接口照常工作”。本轮确认了拒绝写入不会新增资金事实，并验证恢复后的安全重试。

恢复也不是 `redis-cli PING` 成功即所有业务连接恢复：重跑 `20261005_222038` 在首次业务请求遇到了 Redis 旧连接被断开的错误。验收脚本改为保留原幂等键，对暂时错误继续重试，核对最终只有一笔扣款和一条消息；鉴权/业务明确拒绝仍直接使验收失败。
