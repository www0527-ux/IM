# Relay 实时延迟优化（2026-10-06）

## 范围与方法

本轮沿用连接池预算与成功批次立即继续的调度。新增可选分段日志，验证前序检查索引，然后对照完整链路。两轮使用相同服务代码、配置、日志与负载，唯一实验变量是 `idx_relay_predecessor`。

每轮六组消息测试：10/50/100 并发 × 单热门会话/20 会话，每组固定 600 条，阶段间等待 Outbox 与在线推送排空。发送 ACK 表示落库确认；推送耗时从请求开始计至观察连接收到消息。另跑三组领取（每组一个 100 份红包、120 用户）和四组离线同步（每组 3,000 请求）核查回归。编译在启动负载之前完成。

本机 Windows 与 Docker 共享 CPU/磁盘，Kafka 三分区、单副本。单次两轮实验说明本机改善情况，不能作为生产容量保证；原始运行目录保留配置与日志，仓库导出不包含密钥。

## 测量位置与不变的处理顺序

```mermaid
sequenceDiagram
    participant LOOP as Relay循环
    participant W as Worker
    participant DB as MySQL
    participant K as Kafka
    LOOP->>W: R1 RunBatch
    W->>DB: R2 BEGIN，选择到期任务并检查更早未发布Seq
    W->>DB: R3 写租约，COMMIT
    DB-->>W: R4 返回已领取事件
    Note over W,DB: claim计时覆盖R2至R4，包括租约事务
    loop 每条已领取事件
        W->>W: R5 检查取消与租约截止时间
        W->>K: R6 同步发布
        K-->>W: R7 ACK或错误
        Note over W,K: publish计时覆盖R6至R7
        alt ACK成功
            W->>DB: R8 MarkPublished，检查owner、status与租约有效
        else 发布失败或ACK未知
            W->>DB: R9 Reschedule，检查处理权并设置退避
        end
    end
    W-->>LOOP: R10 批次结果；成功有任务立即继续，空批或错误等待
```

R2 仍只领取同会话最早未发布 Seq，使用 `FOR UPDATE SKIP LOCKED`；R3 领取提交成功后才允许 R6 发布。R6～R8 的 ACK 未知、租约过期和回写失败仍可能产生重复发布，接受至少一次投递。增加索引不消除这个故障边界，也不提供多 Relay 严格顺序能力。

`Relay.LogTimings` 默认 `false`，压测开启时输出 `claim`、`publish`、`mark_published`、`reschedule` 的耗时、条数、事件 ID 与失败标记。没有载荷、用户内容或连接凭据。统计回调与日志输出发生在计时结束后；日志自身仍会占用运行时间，两轮使用相同设置。

## 索引验证

在旧压测数据库的独立副本（3,505 行）上执行实际领取 SQL 的 `EXPLAIN ANALYZE`；原库只读。选热门会话的末尾 600/300/100 条改为待发布，每种情况预热一次、测三次。记录的是数据库执行耗时，不含 Docker CLI 启动。原始执行计划见 [分析数据](scripts/relay-index-analysis-20261006.json)。

| 待发布条数 | 原索引（ms） | 状态在 Seq 前（ms） | Seq 在状态前（ms） |
|---|---|---|---|
| 600 | 68.6 / 47.9 / 52.5 | 19.1 / 7.6 / 5.28 | 8.24 / 9.51 / 8.02 |
| 300 | 484 / 506 / 676 | 3.13 / 3.06 / 3.30 | 55.5 / 49.3 / 49.4 |
| 100 | 258 / 290 / 444 | 1.29 / 1.36 / 1.06 | 27.5 / 28.4 / 30.2 |

选择 `(aggregate_type, aggregate_id, event_type, status, aggregate_seq)`。300 条待发布时，原方案对子查询执行 300 次，每次索引扫描平均约 312 行；新方案使用覆盖索引，每次平均约 3.03 行。实际计划仍按前三个等值字段 lookup，再过滤状态和 Seq，不能描述为状态条件已经变成范围扫描。状态在 Seq 前让未发布记录靠前，`EXISTS` 能较早结束；覆盖索引还减少了回表。首个待发布事件仍需确认没有更早的未发布记录。

原查询随着发布推进反复扫描已发布历史，存在累计成本；覆盖索引降低这项成本，但外层仍需扫描候选任务，同会话仍有串行点。新增索引增加存储和状态变更时的维护成本，本轮保留其他索引。

## 数据库故障边界验证

[测试脚本](scripts/test-relay-ordering.ps1) 在新建的 `im_relay_test_*` 库运行真实 MySQL 与真实 Worker，Publisher 注入一次失败。分别以原索引和新索引验证：

- R2 前序行被其他事务锁住：跳过前序，同时不领取后序；其他会话和独立缓存任务仍可领取。
- R6 前序发布失败：R9 将其设置为未来重试，后序保持待发布且不会越过。
- R9 到期后：先重发前序，R8 成功之后，下一批才能发布后序。
- R8/R9 租约过期：更新被拒绝，不抢写状态。

两个索引方案均通过。这里的发布失败是测试 Publisher 注入，尚未模拟真实 Kafka ACK 丢失或进程故障。

## 完整链路对照

两轮各 15,960 次测量请求，均 `PASS`：3,600 次消息发送、360 次领取（300 次成功、60 次已领完）和 12,000 次同步。每轮 3 个红包与 121 名用户资金核查通过，消息数与 Seq 连续性通过，观察连接没有唯一消息的会话内乱序。最终各 3,679 条 Outbox 全部发布，待发布/处理中/重试均为 0，Kafka 有数据分区的消费 lag 均为 0。

| 场景（各 600 条） | 发送 ACK P95：原→新（ms） | 推送 P95：原→新（秒） | 有任务的 ClaimBatch P95：原→新（ms） |
|---|---|---|---|
| 热门会话，10 并发 | 372.95 → 329.91 | 48.950 → 7.323 | 181.255 → 65.287 |
| 热门会话，50 并发 | 1710.27 → 2214.21 | 34.617 → 7.458 | 164.019 → 32.472 |
| 热门会话，100 并发 | 3863.69 → 4018.46 | 47.486 → 9.635 | 183.596 → 28.305 |
| 20 会话，10 并发 | 136.48 → 97.81 | 6.586 → 6.014 | 152.279 → 104.076 |
| 20 会话，50 并发 | 403.55 → 453.38 | 7.359 → 7.550 | 114.437 → 128.819 |
| 20 会话，100 并发 | 933.02 → 1154.04 | 7.128 → 9.809 | 86.789 → 101.176 |

热门会话推送 P95 降低约 79%～85%。100 并发热门会话阶段，领取累计耗时约 49.66 秒降到 10.30 秒；同步 Kafka 发布累计约 0.95 秒与 0.91 秒，状态回写累计约 4.65 秒与 6.22 秒。三个计时相加不能直接当作某条消息的延迟，但说明本阶段收益主要来自领取。新轮真实 ClaimBatch 包括事务、连接和网络，所以不是副本查询的 3ms。

**发送 ACK 没有全面改善，20 会话高并发也未改善。** 新轮 20 会话/100 并发推送 P95 较高，领取与回写计时也较高；新增索引维护成本与共享机器的运行波动都可能影响结果，单次两轮不能区分各自贡献。不能将本轮表述为所有场景性能提升，更不能称为已经达到毫秒级实时容量。当前同会话发布仍串行，100 并发热门会话发送 ACK P95 约 4 秒、推送 P95 约 9.6 秒，仍有容量边界。

两个运行目录分别为 `%TEMP%/im-load-20261006_090415` 和 `%TEMP%/im-load-20261006_090950`。每阶段 Relay 时间窗口从发送开始覆盖到该阶段在线推送排空，可能包含少量未排空的预热事件；事件操作计数不等于该阶段 600 条测量请求数。空批与有任务的领取统计分别保存。

证据：[完整负载数据](scripts/relay-index-results-20261006.json)、[Relay 分段统计](scripts/relay-timings-results-20261006.json)。全部 Go 测试与构建通过。业务测试进程已按 PID 和可执行文件路径检查后停止；Docker 基础设施与隔离测试数据保留。

## 面试讲述

“压测发现热门会话消息已经落库，但推送积压。我将 Relay 拆成领取、Kafka ACK 和状态回写三段计时，发现领取最慢。执行计划显示，前序检查反复扫描已经发布的历史消息。我增加以会话、事件类型、状态和 Seq 排列的覆盖索引，减少回表并使未发布事件靠前。用固定 600 条消息对照，100 并发热门会话推送 P95 从约 47 秒降到 9.6 秒，并验证前序发布失败时后序仍会阻塞。其他多会话场景没有全面改善，当前仍只支持一个有效 Relay。”

## 部署

新库使用更新后的 [outbox_event.sql](sql/outbox_event.sql)。现有库检查 `SHOW INDEX FROM outbox_event` 后执行一次 [迁移 SQL](sql/migrations/20261006_outbox_relay_predecessor_index.sql)。迁移只添加索引；DDL 仍可能等待元数据锁，应在合适窗口执行。回滚命令附在迁移文件中。

本轮已在业务服务停止后，为本地 `infiniteChat.outbox_event` 添加并核对该索引，后续启动即可使用。旧压测源库没有修改。
