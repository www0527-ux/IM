# 06 验证、局限与后续扩展

把“现在是什么”“验证到了什么”“未来怎么做”分开回答。扩展方案是面试讨论，不是当前代码能力。

<a id="f01"></a>
## F01 如何证明项目可靠？哪些故障还没验证？

**口述回答：** 我把验证分成单元测试、真实依赖验收和负载复测。真实验收覆盖幂等发送、并发领取、回滚、部分领取退款、到期竞争、Kafka停机恢复、Outbox重放和浏览器同步交接，核查余额、流水、份额和消息Seq。Relay还有真实MySQL锁竞争与租约恢复测试。但真实网络精确COMMIT或ACK响应丢失、完整DLQ修复重放、多节点接管和长期容量仍未完成，不能用单元测试替代这些保证。

**展开：**

| 验证类型 | 已有证据 | 不能据此宣称 |
|---|---|---|
| Go单元测试/构建 | 分类、重试、确认未知的模拟、WS心跳与顺序测试 | 真实网络所有故障都通过 |
| 真实依赖验收 | 21项后端、浏览器测试；12红包、16用户资金核查 | 全部用户注册/邮件功能、旧库迁移都完成 |
| Relay MySQL集成 | 前序/中间锁冲突、500条前缀、原子确认、租约过期恢复 | 两个存活Relay严格有序接管 |
| 最终本机负载 | 3红包、121用户、65会话核查；Outbox与lag清零 | 100并发无错误、生产多副本容灾 |

**追问：** 资金怎么核查？比较份额与总额、领取记录与已领统计、各业务流水，以及初始余额加流水净额是否等于当前余额；不是只看HTTP成功率。

**代码与证据：** [验收报告](../acceptance-report.md)、[只读核查工具](../service/redpacket/application/audit.go)、[最终负载](../relay-batch-report.md)、[Relay数据库测试](../scripts/test-relay-ordering.ps1)。

**容易说错：** 不把一次测试无差异当作永远正确的形式化证明；当前未运行race detector。

<a id="f02"></a>
## F02 面试官要求多Realtime节点，你会怎么扩展？

**口述回答：** 当前连接只存在本进程Manager，Push组拿到事件的节点不一定持有目标用户连接。直接启动多个相同实例并共用消费组不能保证实时送到。后续可以建立user/device到节点的在线路由并带TTL或心跳，由消费节点查询路由，再通过节点间RPC或按节点通知通道投递到连接所在节点。离线同步和messageID去重仍保留，处理路由过期和节点宕机时的补齐。

**展开：** 给每节点独立消费组广播全部事件也能讨论，易理解但会重复全量消费和接收人查询；节点通知方案减少广播，但引入在线路由生命周期与投递机制。多设备可能属于多个节点，不能把user映射简化成永远一个节点。

**追问：** 网关负载均衡和粘性会话就够了吗？只决定连接建立在哪台节点，不能解决Kafka事件如何找到那台节点。

**代码与证据：** [Manager](../service/realtime/internal/websocket/manager.go)、[Push Consumer](../service/realtime/internal/consumer/message_push_consumer.go)。上述在线路由及节点间通知尚未实现。

**容易说错：** 不说当前已经支持多Realtime，也不凭老师代码有IP字段就断言原项目完成跨节点推送。

<a id="f03"></a>
## F03 Relay能横向扩容吗？租约是否就足够？

**口述回答：** 无顺序依赖的任务可以用租约和数据库领取分摊，但有序消息更严格。当前要求单有效Relay，没有续租或fencing，发布期间过期时旧调用可能继续完成，和新持有者交错。后续可按sessionID固定分片保证同会话一个有效发布者，并设计分片归属、接管和旧发布者隔离。仅在状态回写检查owner不能撤销已经到Kafka的旧发送。

**展开：** 续租降低过期概率，不能单独解决失联旧发布者；fencing只有被实际副作用接收方验证时才有隔离价值。Kafka内部生产者与分片所有权协议要一起评估，不能只给数据库加一个token列就宣布完成。

**追问：** Consumer幂等能代替顺序吗？它能收敛重复，不保证多个发布者送达顺序；客户端按Seq展示是另一个层面的恢复。

**代码与证据：** [当前租约SQL](../service/outboxrelay/internal/relay/store.go)、[Worker](../service/outboxrelay/internal/relay/worker.go)、[接管限制](../relay-batch-report.md)。

**容易说错：** 不说SKIP LOCKED或数据库owner检查自动提供端到端fencing。

<a id="f04"></a>
## F04 网关还缺什么？不做统一限流和动态发现算不完整吗？

**口述回答：** 当前网关完成统一HTTP/WS入口、静态服务转发和构建前端托管，鉴权仍在业务服务。这满足本机单实例学习和演示范围。多实例部署时还需要服务健康与发现、负载均衡、TLS和入口资源控制，并配套进程监督、日志与指标。当前没有宣称这些生产部署能力已经具备；是否做取决于项目范围和部署要求。

**展开：** go-zero服务内路由、User RPC配置和网关入口转发不是同一层。可以复用成熟代理设施，而不是全部手写。权限校验及资金幂等即使加入入口认证或限流仍要保留。

**追问：** 入口限流和业务防超领是一样的吗？不是，前者控制资源消耗，后者是资金正确性约束；当前后者已实现，前者未建设统一方案。

**代码与证据：** [网关README](../service/gateway/README.md)、[Handler](../service/gateway/internal/proxy/handler.go)、[当前范围](../acceptance-report.md)。

**容易说错：** 不说后端项目必须具备所有生产扩展才能讲面试，也不把功能演示可用等同生产就绪。

<a id="f05"></a>
## F05 DLQ重放和监控如果以后做，会怎么做？

**口述回答：** 当前DLQ保存原消费组、topic、partition、offset、内容和原因，稳定位置身份用于识别重复。后续工具应先查询定位、修复原因，再对失败组定向重放，保留业务ID并核对结果；不向所有组无差别广播。监控优先看最老未发布Outbox年龄、PENDING/PROCESSING数量、Kafka lag、重试与DLQ积压、连接池等待和端到端延迟，既看任务推进也看事实核查。

**展开：** 原offset提交仅表示事件被隔离，不表示红包消息已补齐。DLQ保留期、权限、审计与修复操作的幂等需要定义；上述管理工具和持续监控平台当前未实现。现有日志与压测采样不等于生产告警平台。

**追问：** 为什么用户暂时不做？当前优先完成核心业务学习与已列验收，明确保留人工修复工具的范围缺口。

**代码与证据：** [DLQ结构](../service/realtime/internal/consumer/dlq.go)、[分段计时](../service/outboxrelay/internal/relay/worker.go)、[负载资源采样](../scripts/load-monitor.ps1)。

**容易说错：** 不把日志中记录一次错误说成已经有人处理并自动重放完成。

<a id="f06"></a>
## F06 参考老师项目并使用AI，你的工作是什么？

**口述回答：** 项目参考了老师的实现，AI参与了主要代码、配置和验证脚本。我重点参与业务规则和方案取舍，沿发送、领取、退款、同步链路走读，提出关于双写、重复查询、过期检查、游标交接和通知简化的问题，并用代码与真实验收复核结果。面试时我会挑能独立解释的机制展开，明确区分自己的理解与决策、AI实现和参考内容。

**展开：** 按真实过程调整口述，不能把没有亲自执行的操作说成自己手动完成。准备一个可现场解释的片段：为什么事务外查无记录不够、怎样防重复扣款、ACK与offset区别，或Relay批量前缀的失败恢复。

**追问：** AI代码怎么验收？核对事务Session、实际SQL与唯一键、错误分类和成功返回点，再看真实依赖故障与资金/Seq核查；初轮失败也保留，不能只相信生成结果。

**代码与证据：** [开发与学习分工D21](../redpacket-design.md)、[故障问答](04-failures-and-concurrency.md)、[迭代记录](05-iterations-and-performance.md)。

**容易说错：** 不声称全部独立设计和手写；能如实解释一个完整机制，比背未经核对的性能数字更有用。
